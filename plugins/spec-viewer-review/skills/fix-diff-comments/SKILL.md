# Diffコメント修正

spec-viewerの未解決Diffコメントを読み、既存のユーザー変更を保護しながら現在のワークツリーへ修正を反映する。

## コメントを読み込む

1. 対象ファイルに適用される `AGENTS.md` や `CLAUDE.md` を読み、既存のユーザー変更を保護する。
2. 現在作業中のワークツリーに対応するDiffコメント文書を読む。形式の確認が必要な場合は [references/diff-comment-format.md](references/diff-comment-format.md) を参照する。
3. `resolved: false` のコメントを現在のコードと照合し、AIが修正要否を判断する。未解決コメントがなければ、その旨を報告して終了する。

## コメントを評価する

`body` を修正要求として扱い、`replies` を時系列の補足指示として読む。後の返信は元の要求を限定・更新できる。

- `anchor.side` が `current`: `newPath` を編集する。
- `anchor.side` が `base`: `newPath` があればそれを、なければ `oldPath` に対応する現在のファイルを編集する。baseコミット自体は変更しない。

行番号はコメント作成時点のため古い可能性がある。`snippet`、`contextBefore`、`contextAfter`、パス、現在の差分を組み合わせて対象箇所を特定する。

軽微な実装詳細はAIが判断する。対象箇所を一意に特定できない場合や、複数の妥当な実装方針があり選択によって結果が変わる場合だけ、推測せず `AskUserQuestion` など利用可能なAsk系ツールで選択肢と影響を示してユーザーに確認する。

各コメントを次のいずれかに分類する。

- **修正**: 問題が存在し、要求内容も妥当。
- **対応済み**: 現在のコードがすでに要求を満たしている。
- **スキップ**: 指摘が誤っている、リポジトリ規約や別コメントと矛盾する、対象が存在しない、またはアンカーを特定できない。

スキップ時は根拠を具体的に説明する。

## 修正と検証

妥当なコメントごとに最小限の変更を行う。重複するコメントは、修正同士が打ち消し合わないようまとめて扱う。振る舞いが変わる場合はテストを更新し、リポジトリ規約で必要な最小範囲のテスト・lint・型チェック・ビルドを実行する。

修正と検証が完了したコメント、すでに対応済みのコメント、変更不要と根拠を明確に判断できたコメントは解決済みにする。判断を保留したコメントや、修正・検証に失敗したコメントは未解決のまま残す。

コメント文書を更新する直前に再読込し、対象コメントがまだ未解決であることを確認する。[references/diff-comment-format.md](references/diff-comment-format.md) に従って対象の `resolved` と文書の `revision` だけを更新し、他の内容は変更しない。コミット、push、外部コメントへの返信は、ユーザーが別途依頼した場合だけ行う。

## 報告

対象コメントごとに結果を報告する。

```text
- <コメントID> <パス>:<行> — 修正 | 対応済み | スキップ: <結果の要約>
```

最後に検証コマンドと結果、解決済みにしたコメント、未解決のまま残したコメントを示す。
